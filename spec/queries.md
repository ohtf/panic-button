- [x] **Q7 - Windows control API transport.** Resolved 2026-11-14 (Marcus Baw): implement the named pipe as specified, in R32. Implemented as `\\.\pipe\panic-button-<domain>-<user>` with Windows' default pipe security (full access for the owner, SYSTEM and Administrators; read-only for others, which cannot send requests), remote clients refused, and `first_pipe_instance` so the name cannot be squatted. This avoids unsafe Win32 calls to look up the SID and build a custom security descriptor; tighten it to the user's SID and SYSTEM only if Administrators' access is a concern.
- [x] **Q8 - Single-device status after creating a token.** Resolved 2026-11-14 (Marcus Baw): keep the current behaviour and settle the wording in user testing (R33). A practice whose only device has issued an enrolment token shows red "No other devices reachable" rather than amber "No other devices found", because the enroller cert counts as evidence that other devices exist. This errs towards honesty; confirm it is the wording wanted.
- [ ] **Q9 - Admin recovery on a computer that is not in the practice.** FR-ADM-005 and flow D allow recovery "on any enrolled or fresh device". On an enrolled device it works (`admin.recover`). A fresh device can make itself an admin certificate from the kit, but it has no group key, and members only hand over keys after hearing its heartbeat, which is sealed with that key. Two designs: (a) a signed, unsealed key request that members answer with a KeyShare when the sender has a valid certificate; or (b) the recovered device revokes the lost admin computers (as flow D suggests), which rotates to a new key that it shares with every member it learns of. (a) is smaller and keeps the lost admins; (b) is what a compromised-admin recovery needs anyway. Until decided, recover on any computer still in the practice. Raised 2026-11-16.
- [ ] **Q10 - Three spec rules that do not fit what was built.** Found while mapping rules to tests (`rule-coverage.md`, 2026-11-21). (a) Status says amber when "the only reachable path is indirect", but red when "zero peers reachable by any path"; a device that only knows peers from presence summaries cannot send to anyone, and today it shows red, which seems right. Drop the amber rule? (b) "Alarms take priority over heartbeats in processing queues" cannot be done before decryption, because envelopes are sealed and the type is inside. After decryption, the core handles each message at once, so there is no queue to reorder. Drop the rule, or keep it for a future change? (c) Tokens default to 30 days in the spec and the command line, but 7 days in the app's Admin tab. Which should the app use?
